# Redis 캐시 이중화: 캐시를 믿으면 안 되는 이유 (Redundancy)

캐시는 언제든 문제가 생길 수 있는 구성요소라서, 실무에서는 처음부터 이중화 구조로 만들어 둔다. Redis는 순위(랭킹) 처리에 많이 쓰이는데, 한 번 장애가 나면 복구에 하루가 걸릴 수 있다.

## 캐시는 믿을 수 없다
캐시는 안정적인 저장소가 아니라 장애를 전제로 다뤄야 하는 계층이다. 그래서 단일 구성으로 두지 않고 이중화 구조를 미리 만들어 놓는 것이 실무 기본이다.

## 이중화의 목적: 캐시와 DB는 다르다
- 캐시: 데이터 손실을 막기 위해
- DB: 트래픽을 분산하기 위해

메모 원문 표현을 이중화의 목적 차이로 해석해 정리했다. 원문 의도가 다를 수 있어 확인이 필요하다.

## Redis는 순위 계산에 많이 쓰인다
점수 기반으로 등수를 나누는 용도로 자주 쓴다. (보충) 보통 Sorted Set이 이 역할을 한다.

```
ZADD ranking 1500 "user:1"
ZREVRANGE ranking 0 9 WITHSCORES
```

## 한 번 장애 나면 복구에 하루
이중화를 미리 해 두는 이유다. 장애 후 복구에 드는 시간이 길어서, 사후 대응보다 사전 구성이 훨씬 싸다. (복구가 오래 걸리는 구체적 원인은 메모에 없음)

## 내 작업에 적용
- 순위나 실시간 집계 기능에 Redis를 쓸 때, 기능 설계와 함께 이중화 구성과 장애 시 복구 절차를 설계 문서에 넣는다.
