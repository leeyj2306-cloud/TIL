# RAG 평가 기초: 골드 데이터, 지표, 도구 (RAG Evaluation)

RAG는 "잘 되는 것 같다"는 느낌으로 평가하면 그럴듯하게 틀린 답을 놓친다. 골드 데이터(질문·기준 답변·근거)를 만들고, 지표로 검색과 생성을 나눠 채점하고, 결과를 사람이 확인하는 순서로 평가한다. 아래 예시는 모두 강의의 가상 장비 대여 규정이다.

## 오류는 검색 오류와 생성 오류로 나눠 본다
질문 "노트북은 며칠 빌릴 수 있나요?"

| 검색한 문서 | 생성한 답변 | 판정 |
|---|---|---|
| 프린터 규정: 최대 14일 | 노트북은 14일 | 검색 오류 |
| 노트북 규정: 최대 7일 | 노트북은 14일 | 생성 오류 |

답변만 보면 둘 다 "14일"이라 구분되지 않는다. 검색한 문서를 답변과 함께 기록해야 한다.

## 평가 데이터: 공개 벤치마크와 골드 데이터셋
- 공개 벤치마크는 같은 문제·같은 채점 기준으로 시스템끼리 비교하는 용도다. BEIR는 검색 성능, HotpotQA는 여러 근거를 연결하는 질의응답을 본다.
- 한국어는 Allganize RAG-Evaluation-Dataset-KO(5개 분야 300문항, 질문 + 기준 답변 + 정답 문서·페이지)로 점검할 수 있다. 공개 문서 색인 → 같은 질문 실행 → 정답·근거 대조 순서다.
- 공개 질문("두 인물의 공통 출생지는?")은 우리 서비스의 질문과 성격이 달라서, 서비스용 골드 데이터가 따로 필요하다.
- 골드 한 건은 질문 + 기준 답변 + 근거(예: policy-01 / v1 / 제3항)다. LLM이 초안을 만들고 사람이 원문과 대조해 확정한다. 초안이 "14일"이어도 원문이 "최대 7일"이면 원문을 따른다.
- 질문은 세 유형을 섞는다.
  - 단순 사실: 노트북은 며칠 빌릴 수 있나요? → 최대 7일
  - 여러 조건: 재학생인데 10일 빌릴 수 있나요? → 가능하지만 최대 7일 (대상 조항 + 기간 조항)
  - 답 없는 질문: 연장할 수 있나요? → 문서로는 확인할 수 없어요

## 평가 지표: 무엇을 무엇과 비교하나

| 지표 | 비교 대상 | 확인하는 것 |
|---|---|---|
| Recall@k | 검색한 근거 ↔ 필요한 근거 | 필요한 근거를 찾았나 |
| Faithfulness | 생성 답변 ↔ 검색 문서 | 검색 문서에 근거했나 |
| Factual Correctness | 생성 답변 ↔ 기준 답변 | 기준 답변과 일치하나 |
| Answer Relevance | 생성 답변 ↔ 사용자 질문 | 질문에 답하고 있나 |

Recall@3 예: 필요한 근거 A·B 중 상위 3개에 A만 있으면 1/2 = 0.5. (보충) Recall@k = 상위 k개 안의 필요한 근거 수 / 필요한 근거 전체 수.

## 평가 도구: Ragas와 TruLens
- Ragas는 질문셋을 한꺼번에 채점할 때 쓴다. 입력은 질문·기준 답변·실제 답변·검색 문서다. 흐름은 지표·평가용 LLM 설정 → `scorer.ascore(...)` 호출 → 질문 ID별 점수 저장이다.

```json
{
  "user_input": "노트북은 며칠 빌릴 수 있나요?",
  "reference": "최대 7일입니다.",
  "response": "최대 14일, 한 번 연장 가능합니다.",
  "retrieved_contexts": ["노트북 대여 기간은 최대 7일입니다."]
}
```

- Faithfulness는 답변을 주장으로 나눠 문서가 뒷받침하는 비율을 본다. 위 답변은 "최대 14일"(문서는 7일), "한 번 연장 가능"(문서에 없음) 둘 다 뒷받침되지 않아 0/2 = 0이다.
- TruLens는 실행 단계별로 원인을 찾을 때 쓴다. 요청 처리·검색·생성 함수에 기록을 연결하면 run별로 펼쳐 볼 수 있다. 예: Q001 / run-001은 검색이 7일 규정을 찾았는데 생성이 14일로 답했으니 생성 단계 문제다.
- TruLens의 세 관점: Context Relevance(질문 ↔ 검색 문서), Groundedness(검색 문서 ↔ 답변), Answer Relevance(질문 ↔ 답변). (보충) RAG Triad.
- 돌리기 전에 3건으로 토큰·비용부터 확인한다. 평가용 API 비용은 별도다.
- 한국어에서는 "연장 정보 없음"과 "연장 불가"를 채점이 같게 취급할 수 있으니 결과를 사람이 확인한다.

## 운영: 파일 관리와 결과 분석
- 파일은 gold_v1.jsonl(질문·기준 답변·근거)과 run_001.jsonl(실제 답변·검색 문서·평가 결과)로 나누고, 질문 ID + 평가셋 버전으로 연결한다.
- 결과는 유형별로 묶어 본다. 가상 예: 단순 사실 9/10, 여러 조건 4/10, 답 없는 질문 8/10이면 여러 조건이 약점이다. 실패 답변("재학생이니 가능해요")을 기준 답변("가능하지만 최대 7일")과 비교하면 놓친 조건이 기간임을 알 수 있다.
- 첫 평가는 세 유형 × 10개로 시작한다. 질문·기준 답변 검토 → RAG 실행·기록 → 도구로 채점 → 실패 사례 확인 순서다.
- 채점하는 AI도 검증 대상이다. 점수가 높아도 원문과 기준 답변을 확인한다. RAG 밖에서도 같아서, 회의 요약이면 담당자·기한·할 일 기준을 먼저 정하고 입력과 AI 결과를 기록한 뒤 원문과 대조한다.

## 내 작업에 적용
- RAG 실행 로그에 답변과 함께 검색된 문서의 ID·버전·조항을 저장해 오류를 검색과 생성으로 가른다.
- 팀 프로젝트의 평가셋은 유형 태그를 붙여 같은 개수씩 만들고, 프롬프트나 검색 설정을 바꿀 때마다 run 파일을 새로 만들어 같은 gold 버전으로 비교한다.
- 팀 회의록을 AI로 요약할 때도 체크 기준을 먼저 정하고 원문과 대조한 뒤 공유한다.
