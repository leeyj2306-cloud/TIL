# 정형 검증 에이전트 스킬로 회귀 버그 막기 (Proof Skills & Agent Formalize)

바이브 코딩으로 빨리 만든 프로젝트는 커질수록 기존 기능이 깨지는 회귀 버그가 잦아진다. 단위 테스트로 다 막을 수 없는 동시성·상태 전이 구간을 수학적 정형 검증 스킬로 증명하되, 비용이 크니 고위험 변경에만 골라 쓰자는 내용이다.

## 왜 단위 테스트만으로 부족한가
- 에이전트는 지정된 코드 영역만 깊게 본다(망원경 효과). 전체 구조를 못 봐서 국소 수정이 사이드 이펙트를 낸다.
- 테스트는 작성자가 떠올린 시나리오만 검증한다. 이벤트 10개가 교차하면 실행 순서만 10! = 3,628,800가지라 테스트·퍼징으로 전수 확인이 안 된다.
- 정형 검증은 샘플 대신 불변식(Invariant)을 정의하고, 도달 가능한 모든 상태 공간을 탐색해 깨지는 경로(반례)를 찾는다. 명세 자체가 틀린 경우는 못 잡는다.

## 두 도구의 동작 방식
- **proof-skills (Claude Code)**: 상태 전이 정리 → 불변식 정의(예: `재고 >= 0`, 이중 출금 불가) → TLA+ 모델 체커(TLC)나 Lean 4로 반례 탐색 → 반례 경로를 컨텍스트로 넣어 코드 재설계.
- **agent-formalize (Codex)**: 자연어 PRD를 정형 사양으로 바꾸고, 사전·사후 조건을 Z3/Lean 4로 검증해 증명 통과를 커밋 게이트로 둔다.
- 둘 다 `SKILL.md`·MCP 기반이고 실제 검증은 로컬 바이너리(`tlc`, `lean`, `z3`)가 하므로 `~/.claude/skills/` ↔ `~/.codex/skills/`로 옮겨 쓸 수 있다고 한다.

## 비용과 트레이드오프
자료가 제시한 수치는 커버리지 약 54% → 98%, 작업 시간 약 2.4배, 토큰 약 2.2배다(출처·측정 조건이 자료에 없어 미검증). UI 스타일링, 정적 페이지, 단순 CRUD에 상시 적용하면 낭비다.

## AGENT.md / CLAUDE.md에 넣을 선별 호출 룰
```markdown
## 정형 검증 스킬 조건부 호출
상시 가동하지 않고 아래 고위험 변경에만 호출한다.
1. 동시성: 분산 락, DB 트랜잭션 격리 수준, 멀티스레드 동기화 변경
2. 복합 상태 머신: 3개 이상 기능이 맞물려 순서 의존성이 큰 로직
3. 핵심 불변식: 결제, 정산, 재고 차감, 계정 권한
단순 UI, 데이터 표시, 독립 유틸 함수는 표준 단위 테스트로 대신한다.

## 검증 실패 시
- 반례나 불변식 위반이 나오면 땜질성 예외 처리를 쓰지 않는다.
- 변경 전 상태로 롤백한다.
- 위반된 상태 전이 트레이스 분석과 구조적 수정안 2가지를 먼저 보고한다.
```
도입 전 준비: 로컬에 `tla-bin`, `lean4`, `z3` CLI 설치, 코드가 안 바뀐 상태 머신은 재증명하지 않도록 캐시 규칙 마련.

## 원문 연구: 기존 테스트를 명세로 바꿔 증명하기 (Anthropic, 2026-10)
- 명세 작성이 가장 어려운 부분인데, 이미 있는 퍼즈 테스트를 "어떤 입력(64MB 미만)에도 이 테스트는 크래시하지 않는다"는 명세로 바꿔 우회했다.
- Claude가 OSS-Fuzz 라이브러리 123개, 진입점 239개를 RISC-V 바이너리 수준에서 Rocq로 증명했다. 증명 코드는 약 1억 8천만 줄이지만 Rocq 검사기가 확인하므로 사람이 리뷰할 필요는 거의 없다.
- 루프: 증명 시도 → 막히면 버그 후보 → 패치 → 명세 재생성 → 재증명. 증명을 끝내지 못해도 시도 과정에서 실제 버그가 나온다.
- 퍼저가 놓친 사례: 약 20MB의 특정 배치 입력에서만 터지는 범위 밖 쓰기, 같은 파일의 두 핸들을 특정 순서로 호출할 때만 생기는 범위 밖 읽기, 크래시 없이 파일 로딩 제한이 안 걸리는 논리 버그.
- 리워드 해킹 방지: 에이전트가 프로그램을 "아무것도 안 하게" 고쳐 증명을 통과시킬 수 있어서, 패치에는 감점을 주고 영향받는 입력 범위를 증명하면 가산점을 줬으며 패치를 기록·감사했다.
- 한계: "정형 검증됨"은 "버그 없음"이 아니다. 단일 스레드·정적 링크·RISC-V·musl 가정이라 실제 배포 환경(x86/ARM, glibc, 멀티스레드)과 차이가 있고, 명세가 다루지 않는 영역은 보장하지 않는다. 즉 영상이 말하는 동시성 버그는 이 연구의 증명 범위 밖이다.
- 비용은 줄어드는 중: 증명 하나에 수억 토큰이 들 수 있지만, 에이전트끼리 증명을 공유하면 토큰이 약 17% 줄었다. Theorem이 직접 검증을 시작할 수 있는 Claude 스킬을 공개했다.

## 내 작업에 적용
- BidLive 실시간 입찰은 동시 입찰·낙찰 확정이 맞물리는 전형적인 고위험 구간이다. "최고 입찰가는 감소하지 않는다", "낙찰자는 한 명" 같은 불변식을 먼저 문장으로 정의해 두면 검증 도구를 안 쓰더라도 테스트·리뷰 기준이 된다.
- 명세를 새로 쓰기 막막하면 이미 있는 테스트의 단언(assert)을 불변식 후보로 삼는다. 입찰·결제 테스트의 기대값을 "항상 성립해야 하는 규칙"으로 옮겨 적는 것부터 시작할 수 있다.
- 팀 프로젝트 CLAUDE.md에 위 선별 호출 룰과 실패 시 롤백·대안 보고 규칙을 넣어 에이전트의 무분별한 리팩토링을 막는다.
