# 애자일과 스크럼: 데일리 스크럼 진행법과 스토리 포인트 (Agile & Scrum)

애자일은 변화와 고객을 중심에 두고 작게 반복하며 가치를 빨리 전달하는 방식이고, 스크럼은 그 대표 프레임워크다. SSAFY 프로젝트가 애자일 기반으로 진행되므로, 데일리 스크럼을 제대로 굴리는 법과 스토리 포인트 기준을 정리했다.

## 애자일이 필요한 이유
폭포수(waterfall)처럼 분석→설계→개발→테스트를 순서대로 밟으면, 진행 중에 고객이 학습해 원하는 것이 명확해져도 반영하기 어렵다. 프로세스 중심 방식은 통제적이고 경직되어 변화에 느리다(단, 폭포수가 맞는 경우도 있다).
애자일 선언문은 협업·커뮤니케이션, 문서 뭉치보다 동작하는 소프트웨어, 변화 수용을 강조한다. 특징은 반복적·점진적 진행, 경험적 통제, 기능 혼합 팀(Cross Functional Team), 고객 참여, 자기조직화(리더는 지원하는 역할)다.

## 스크럼의 기본 구성
- **스프린트**: 1~4주 개발 주기. 시작할 때 목표와 스프린트 백로그를 정하고, 끝나면 리뷰와 회고를 한다.
- **백로그**: 모든 업무를 우선순위로 정렬한 목록. 요구사항 정의서 역할도 하며 수시로 추가·삭제·변경된다. 새로 들어온 항목은 다음 스프린트에 반영한다.
- **스크럼 마스터**: 팀장이 아니라 진행이 잘 굴러가게 돕는 사람. 데일리 스크럼 진행, 시간 조정, 막힌 이슈·팀 규칙·일정 리스크를 챙긴다.

## 데일리 스크럼: 보고가 아니라 싱크
매일 아침 같은 시간에 10~15분(6명이면 1인 1~2분). 각자 **어제 한 일 / 오늘 할 일 / 막힌 점** 순서로 말한다.
진행: 스크럼 마스터가 시작 → 각자 공유 → 막힌 항목 표시 → 전체 논의가 필요한 것만 짧게 확인 → 길어질 기술 논의는 별도 미팅. 끝나면 Jira·칸반 보드를 바로 업데이트한다.
피할 것: 한 명의 문제를 다 같이 디버깅, 못한 이유 추궁, 팀장에게 보고하듯 말하기, "어제 하던 거 이어서"로 끝내기, 막힌 점 숨기기.

```text
나쁜 예: 어제 프론트 했습니다. 오늘도 이어서 하겠습니다.
좋은 예: 어제 로그인 페이지 UI를 만들었고, 오늘은 로그인 API와 연결합니다.
        에러 응답 형식이 아직 안 정해져서 오전에 백엔드와 맞춰야 합니다.
```

## 스토리 포인트 기준
작업 크기·난이도를 맞추기 위한 추정 단위다. 사람을 평가하는 도구가 아니다.

| 점수 | 기준 | 예시 |
|---|---|---|
| 1 | 작고 명확 | 버튼 문구, 간단한 CSS, 정해진 명세에 맞춘 필드명 수정 |
| 2 | 하루 안에 끝날 일반 작업 | 단일 API, 간단한 페이지 UI, 입력값 검증 |
| 3 | 고민 필요·다른 작업과 연결 | 로그인, 프론트-백엔드 API 연동, ERD 수정이 따르는 기능 |
| 5 | 불확실성 크고 하루를 넘김 | 소셜 로그인 전체, 실시간 채팅, 배포 환경, 외부 API·AI 모델 연동 |

데일리 스크럼에서는 점수를 다시 계산하지 않고 상태 점검에 쓴다. 2점짜리가 왜 안 끝났나, 5점을 혼자 맡고 있으면 쪼갤 수 없나, 3점 이상이 많으면 주간 목표가 과한가, 큰 작업이 한 명에게 몰렸나. 5점은 가능하면 더 작게 나눈다.

## 스크럼 직후 자가진단
- 각자 오늘 할 일, 막힌 사람, 오늘 내려야 할 의사결정을 모두 알고 있는가
- 주간 목표 대비 일정이 위험하지 않은가, 큰 작업이 방치되거나 한 명에게 몰려 있지 않은가

## 내 작업에 적용
- 팀 프로젝트에서 스크럼을 진행할 때 "막힌 점"을 결정 항목(예: 에러 응답 형식, 저장할 필드)으로 바꿔 담당자와 시한을 그 자리에서 정한다.
- simAI처럼 AI API 작업이 있는 프로젝트는 "AI 모델 연동"이 통째로 5점이 되기 쉬우므로, 프롬프트 설계·API 명세·연동 테스트로 쪼개 백로그에 올린다.
